Lesson 04 of 05

The Coin Flow

🏆 Win: Trace a coin from the kid's tap all the way to the ledger

Why This Is the Core Feature

Everything in Earnie revolves around coins. The task system creates coins. The goal system tracks them. The reward system spends them. If you understand the coin flow end-to-end, you understand ~80% of the app's complexity.

There are two flows that are mirrors of each other:

  • Earning: Task → task_completions → parent approval → coin_transactions(earned)
  • Spending: Reward request → redemption_requests → parent approval → coin_transactions(redeemed)

Earning Path (Task → Coins)

Step 1 — Kid taps "Mark Done"

// KidContext.addCoins() is called IMMEDIATELY (optimistic)
setBalance(prev => prev + task.coinReward);

// Then the API call happens
POST /api/tasks/completions
Body: { taskId, kidId, coinsEarned }

Step 2 — API inserts a pending completion

INSERT INTO task_completions
  (task_id, kid_id, coins_earned, status='pending', completed_at=now())

An activity_log row of type task_completed is also appended here.

Step 3a — Parent approval required (require_task_approval = true)

// Parent sees pending item on /parent/home
// Taps "Approve"
PATCH /api/tasks/completions/[id]
Body: { action: "approve" }

// Server runs (one DB transaction):
UPDATE task_completions SET status='approved', resolved_at=now()
UPDATE kid_profiles    SET balance = balance + coins_earned
INSERT INTO coin_transactions (type='earned', amount, description)
INSERT INTO activity_log      (type='task_approved', payload={…})

Step 3b — Auto-approve (require_task_approval = false)

The API skips the pending state entirely — all four writes happen on insert. The kid's balance updates before the parent even sees it.

On denial: status = 'denied', and the optimistic coin update in KidContext must be rolled back. The server sends back { status: 'denied' } and the kid's UI calls addCoins(-task.coinReward).

Optimistic UI in KidContext

The kid's coin balance updates instantly when they tap "Mark Done" — before any API response. This makes the app feel snappy and rewarding for kids who need immediate feedback.

// src/context/KidContext.tsx
const addCoins = useCallback(
  (delta: number) => setBalance(b => b + delta),
  []
);

// Usage in task page:
function handleMarkDone(task: Task) {
  addCoins(task.coinReward);           // immediate UI update
  fetch('/api/tasks/completions', …)   // background API call
    .then(res => {
      if (res.status === 'denied') addCoins(-task.coinReward); // rollback
    });
}

Current state: KidContext uses a mock session (useMockKidSession). The real Supabase-backed implementation is the #1 pending integration task. The addCoins interface will stay the same — only the data source changes.

Spending Path (Reward Redemption)

The redemption flow is a structural mirror of the earning flow:

Kid taps Redeem
→
redemption_requests (pending)
→
Parent approves
→
coin_transactions (redeemed) − coins

Key difference: coins are deducted on approval. The optimistic UI on the kid side should show the reward as "pending" (greyed out / badge) rather than immediately deducting balance — because kids find balance going down confusing before approval.

// On redemption approval (server-side):
UPDATE redemption_requests SET status='approved', resolved_at=now()
UPDATE kid_profiles        SET balance = balance - coins_spent
INSERT INTO coin_transactions (type='redeemed', amount=-coins_spent, …)
INSERT INTO activity_log      (type='reward_approved', payload={…})

Cross-Device Sync via Supabase Realtime

A parent approves a task on their phone. The kid's tablet needs to update its coin balance without a page refresh. This is handled by Supabase Realtime.

// Kid's client subscribes to their kid_profiles row
supabase
  .channel('kid-balance')
  .on('postgres_changes', {
    event: 'UPDATE',
    schema: 'public',
    table: 'kid_profiles',
    filter: `id=eq.${kidId}`,
  }, (payload) => {
    // Update KidContext balance from payload.new.balance
    setBalance(payload.new.balance);
  })
  .subscribe();

The Realtime subscription acts as a reconciliation layer — even if the optimistic update was slightly wrong (e.g., auto-approve happened differently), the real balance syncs down.

Manual Coin Adjustment

Parents can adjust a kid's balance directly (positive or negative). This creates a coin_transactions row with type = 'adjusted' and the delta as amount (can be negative).

Always write the reason to description — it shows up in the activity feed and coin history. The activityLog entry type is coins_adjusted.

🧠 Retrieval Check

1. A kid marks a task done. List exactly what happens in the next 5 seconds, in order, including what the kid sees vs what the DB state is.

Reveal answer
t=0: Kid taps "Mark Done". KidContext immediately adds coins (optimistic) — kid sees balance increase.
t=0ms: API call fires in background: POST /api/tasks/completions.
t=~100ms: DB inserts task_completions with status='pending' + activity_log(task_completed).
t=~100ms: API responds — kid UI shows task as "pending approval" (if require_task_approval=true).
Later: Parent approves → DB updates 4 rows in one transaction. Supabase Realtime pushes balance update to kid's device.

2. A parent denies a task. What must the client do that it wouldn't do on approval?

Reveal answer
Roll back the optimistic coin update. Call addCoins(-task.coinReward) to subtract the coins that were added immediately when the kid tapped done. No DB write is needed on the client — the server already set status='denied' and did not credit coins.

3. How would you correct a kid's balance if an incorrect coin_transactions row was inserted?

Reveal answer
Never update or delete the incorrect row — it's an immutable ledger. Insert a new coin_transactions row of type='adjusted' with the corrective delta (e.g., if 20 coins were incorrectly credited, insert amount=-20). Also update kid_profiles.balance by the same delta. Write a clear description explaining the correction.
