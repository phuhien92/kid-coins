Auth & Sessions

🏆 Win: Explain the auth model to a security reviewer without notes

Two Auth Models, One App

Earnie has two completely different auth strategies for its two users — and this is by design:

Parents

  • Full Supabase Auth account
  • Email + password login
  • Standard JWT session managed by Supabase
  • Optional 4-digit PIN for the profile picker

Kids

  • No Supabase Auth account
  • 4-digit PIN only (age-appropriate)
  • PIN is verified server-side, then a short-lived session token is issued
  • Their identity lives entirely in kid_profiles

Kids cannot log in independently — a parent must first authenticate, then the profile picker allows switching to a kid's session. The family is always the root auth unit.

Parent Auth Flow

1. POST /auth/v1/token (Supabase)
   → Email + password → Supabase JWT (access + refresh tokens)
   → Supabase UID stored as families.parent_user_id

2. GET /profile-picker
   → Supabase session confirmed via server client
   → Lists all kid_profiles for this family

3. (Optional) Parent PIN gate
   → If families.parent_pin_hash is set, profile picker shows PIN prompt
   → POST /api/parent/verify-pin  →  bcrypt.compare(input, hash)
   → On success: opens /parent/home

No PIN set? The parent tile on the profile picker opens /parent/home directly — no PIN prompt shown.

Kid Auth Flow

1. Parent is authenticated → /profile-picker shows kid tiles

2. User taps a kid tile
   → If kid has a PIN: PIN pad shown
   → POST /api/kids/[id]/verify-pin  →  bcrypt.compare(pin, kid_profiles.pin_hash)

3. On success:
   → POST /api/kids/[id]/session  →  issues a signed session token
   → Redirect to /kid/home

4. All kid-facing API calls carry this session token
   → Server extracts kid_id from token, never from URL params

Kids have no Supabase auth accounts. Never try to call Supabase Auth APIs for a kid. Their entire identity is a row in kid_profiles — the session token is the only thing that gives them access.

PIN Hashing

Both parent and kid PINs use bcrypt hashing. The hash is stored in:

  • families.parent_pin_hash — optional, null when no parent PIN is configured
  • kid_profiles.pin_hash — always set (required to create a kid profile)

Verification flow is always bcrypt.compare(userInput, storedHash). The raw PIN is never stored, logged, or transmitted after the initial creation.

Why bcrypt for a 4-digit PIN? 4-digit PINs have only 10,000 possibilities — bcrypt's cost factor prevents brute-force even if the DB leaks. The UX cost (slightly slower hash check) is acceptable.

The Auth Proxy

Route protection lives in src/proxy.ts. This Next.js middleware runs before every request and:

  • Checks for a valid Supabase session on /parent/* routes
  • Checks for a valid kid session token on /kid/* routes
  • Redirects unauthenticated requests to /login

You don't need to add auth guards inside individual pages — the proxy handles it. But if you add a new route group, make sure it's covered by the proxy rules.

🧠 Retrieval Check

1. Can a kid log into Earnie without a parent being involved at all? Why or why not?

Reveal answer
No. Kids have no Supabase Auth accounts and cannot start a session independently. A parent must first authenticate (Supabase email/password), which unlocks the profile picker. From there, a kid's session token is issued via POST /api/kids/[id]/session — but only after the parent's session is active on the device.

2. A parent sets up a 4-digit PIN for themselves. Where is it stored and how is it verified?

Reveal answer
Stored as a bcrypt hash in families.parent_pin_hash. When the parent tile is tapped on the profile picker, a PIN pad appears. The input is sent to POST /api/parent/verify-pin, which runs bcrypt.compare(input, families.parent_pin_hash). On success, the parent is redirected to /parent/home. The raw PIN is never persisted.

3. You're adding a new page at /parent/reports. What do you need to do to ensure unauthenticated users can't access it?

Reveal answer
Check src/proxy.ts to confirm the middleware already covers /parent/* routes. If it does, no page-level changes are needed — the proxy will redirect unauthenticated requests to /login automatically. If the proxy has an explicit allowlist, add /parent/reports to the protected paths.
