The Core Hierarchy

Think of the schema in three layers:

Layer 1 — Family (account root)

families (id, parent_user_id, name, parent_pin_hash)
  └── family_settings (require_task_approval, require_redemption_approval, …)
  └── rewards (family-wide catalog — shared by all kids)
  └── activity_log (event stream for parent dashboard)

Layer 2 — Kid (one per child)

kid_profiles (id, family_id, name, pin_hash, balance)
  └── characters (hat, eye, color, bg, outfit)   ← 1:1
  └── streaks (current_streak, longest_streak)    ← 1:1
  └── tasks (assigned chores — per kid, not per family!)
  └── goals (savings targets)
  └── badges (achievement slugs)

Layer 3 — Events (immutable records)

task_completions  (task_id → kid_id, status: pending|approved|denied)
coin_transactions (kid_id, type: earned|redeemed|adjusted, amount)
redemption_requests (kid_id → reward_id, status: pending|approved|denied)

Critical: Tasks belong to a kid (kid_id FK), but rewards belong to the family (family_id FK). A reward catalog is shared; a task list is personal.

The Coin Ledger Pattern

kidProfiles.balance is a cached aggregate — fast to read, but the source of truth lives in coin_transactions.

Three transaction types

TypeTriggerAmount sign
earnedTask completion approvedPositive (+coins)
redeemedRedemption request approvedNegative (−coins)
adjustedParent manual adjustmentEither (delta can be negative)

Never update or delete coin_transactions rows. They are an immutable audit trail. If you need to correct a balance, issue an adjusted transaction with the delta.

Balance consistency rule

Whenever coin_transactions gets a new row, kid_profiles.balance must be updated in the same DB transaction. The API layer handles this — if you write a new route that credits coins, follow the same pattern.

Two Approval State Machines

Both tasks and redemptions use the same three-state flow:

task_completions

pending
→ approve →
approved ✓ (coins credited)
pending
→ deny →
denied ✗ (optimistic rolled back)

redemption_requests

Exact same shape: pending → approved (coins deducted) or pending → denied (no change).

Auto-approve shortcut: If family_settings.require_task_approval = false, the API auto-approves on insert — skipping the pending state entirely. Same for require_redemption_approval.

The Activity Log

An append-only event stream. The payload field is freeform JSON whose shape depends on type:

// task_approved
{ taskTitle: "Make your bed", coinsEarned: 2, completionId: "uuid" }

// reward_redeemed
{ rewardTitle: "Extra screen time", coinsSpent: 30, requestId: "uuid" }

// coins_adjusted
{ delta: -10, reason: "Late chores penalty" }

This is how the parent dashboard activity feed is populated. Never delete rows — this is a historical record.

Schema Change Workflow

  1. Edit src/lib/schema.ts
  2. Run pnpm db:generate — creates a migration file in drizzle/
  3. Run pnpm db:migrate — applies it (requires DATABASE_URL)
  4. Commit both the schema change and the generated migration file

Never edit migration files manually. If a migration goes wrong, write a new one that corrects it.

🧠 Retrieval Check

1. You need to display a kid's task list and also the family's reward catalog. Which tables do you query, and what FK do each use?

Reveal answer
Tasks: tasks WHERE kid_id = ? — tasks belong to a kid.
Rewards: rewards WHERE family_id = ? — rewards belong to the family (shared by all kids in that family).

2. A parent approved a task. List every DB write that must happen (in one transaction).

Reveal answer
1. UPDATE task_completions SET status='approved', resolved_at=now() WHERE id=?
2. UPDATE kid_profiles SET balance = balance + coins_earned WHERE id=?
3. INSERT INTO coin_transactions (kid_id, type='earned', amount, description)
4. INSERT INTO activity_log (family_id, kid_id, type='task_approved', payload={…})

3. What is the difference between characters and kid_profiles.avatar_color? When do you use each?

Reveal answer
kid_profiles.avatar_color is a simple hex color used for the kid's initial avatar/profile chip in the profile picker — it's decorative metadata on the profile itself.

characters is a full customization record (hat, eye, color, outfit, bg, extra) for the in-app mascot displayed in Character Studio. It's 1:1 with kid_profiles and is synced independently. Changing a character outfit doesn't change the avatar color shown in the profile picker.
